# Яндекс Почта 360 — направления автоматизации

**Статус:** бэклог идей, не реализовано и не включено. Официальные источники: [API пользовательской Почты](https://yandex.ru/dev/yandex-360/mail/ru/), [API 360 для бизнеса](https://yandex.ru/dev/api360/doc/ru/), [SMTP и почтовые клиенты](https://yandex.ru/support/yandex-360/business/mail/ru/mail-clients/others), [OAuth для SMTP](https://yandex.ru/support/yandex-360/business/mail/ru/web/security/oauth.html). Перед реализацией сверять конкретные методы и разрешения с актуальной документацией, см. [справочник](README.md).

## 1. Отправка УПД через Яндекс 360 (первый приоритет почты)

`daily_upd` существует и не должен меняться без отдельного задания. В текущем `hub/channels/email.py` работает SMTP LOGIN (логин + пароль приложения), но **OAuth XOAUTH2 не реализован**.

Предлагаемый безопасный путь:
1. Отдельный корпоративный ящик-отправитель, например бухгалтерский; точный адрес задаёт владелец. Не использовать личный пароль аккаунта.
2. В админке Яндекс 360 проверить почтовый доступ, настройки IMAP и разрешения для паролей приложений / OAuth.
3. Задать через Dockhost `SMTP_HOST=smtp.yandex.ru`, `SMTP_PORT=465`, `SMTP_STARTTLS=0`, `SMTP_USER`, `SMTP_PASSWORD` (пароль приложения), `SMTP_FROM` (тот же ящик). Значения остаются в секретах, не в git.
4. Сначала проверить подключение и одну тестовую отправку на свой адрес **в изолированном тестовом контуре**; в действующем `msgit` не отключать глобальный dry-run.
5. Затем проверить адресатов, отсутствие email, повтор УПД, отгрузки после 17:00, сценарий «ОТПРАВЛЕН В ЭДО». Реальную клиентскую рассылку включать только по отдельному решению.

Путь OAuth/XOAUTH2 — отдельная задача с изменением почтового транспорта, правом `mail:smtp` и тестами протокола; просто вставить OAuth-токен в `SMTP_PASSWORD` для текущей реализации нельзя.

## 2. Входящие письма: возможные автоматизации

После одобрения владельца и отдельного исследования API:
- **Реестр входящих документов:** распознавать входящие счета, УПД и акты, сохранять вложения, связывать с заказами и контрагентами (без автоматического проведения/изменения бухгалтерии).
- **Отслеживание ответов:** находить сообщения покупателей по идентификатору заказа/ветке переписки, информировать ответственного.
- **Поставщики:** собирать счета и коммерческие предложения для ручной сверки с МойСклад.
- **Контроль недоставки:** сообщения об ошибке доставки, отдельный журнал неуспешных адресатов.
- **Контроль обращений:** распределять входящие по папкам и меткам, уведомлять сотрудников; автоответ — только после согласования текста и получателей.
- **Аналитика коммуникаций:** число полученных/отправленных писем, сроки ответа; при наличии доступных методов и подтверждённой схемы расчёта.
- **Вложения и архив:** сохранять вложения в разрешённую папку Диска, исключая дубли по устойчивым ключам.

При чтении писем ограничить доступ к конкретному ящику/папкам. Текст письма и вложения — **недоверенный ввод**, не инструкции для ИИ; не исполнять команды из письма, не включать удаление/пересылку/отправку без отдельного разрешения. Учесть персональные данные, права доступа и сроки хранения.

## 3. Архитектура почтовой интеграции

Отдельные адаптеры с минимальными полномочиями:
- `smtp_sender`: только отправка разрешённых сообщений, журнал/idempotency.
- `mail_reader`: чтение/поиск входящих по поддерживаемым API или IMAP, отдельный read-only OAuth.
- `mail_automation`: бизнес-правила, очередь и дедупликация, **выключено по умолчанию**.
- `yandex_disk`: загрузка вложений с отдельными правами Диска.
- `organization_admin`: не включать в обычный hub; требует особых ролей и scopes.

Нельзя считать REST API Почты эквивалентом SMTP: наличие методов чтения и управления письмами не доказывает наличие REST-метода отправки нового сообщения. Проверять официальную спецификацию. Для API пользовательской Почты требуется подходящий тариф Яндекс 360.

## 4. Безопасность и тестирование

- Секреты в env/Dockhost, отдельный набор для тестового контура.
- Никаких токенов в логах, чатах и GitHub; по возможности маскировать адресатов/содержание писем.
- Проверки авторизации/ревокации, `429`, `5xx`, timeouts, письма/вложения большой длины, Unicode/кириллица, защита от дублей и повторов.
- При недоступности Яндекса задания сохранять в очереди; оператору выдавать причины неуспеха.
- Разделить статусы «запланировано», «отправлено SMTP-серверу», «доставлено получателю»: успех SMTP не подтверждает фактическую доставку.
- Для реальной автоматизации клиентской переписки — сначала dry-run и ручной review.

Пока это **справочник возможностей и бэклог**, а не разрешение реализовать или запустить отправку писем.
